# 网球小游戏原型：测试策略

被测版本：`index.html`。单个 HTML/JS 文件，没有任何依赖，包含四种模式：发球机、对打 AI、双人对战、双打。
配套文档：`tennis-game-test-cases.md`（90 条用例，14 节）。本文说明这些用例*为什么*测、*怎么*测，不重复列用例。

---

## 1. 目的

这个原型只为回答一个问题：**击球手感好不好、公不公平？** 测试的目标是尽快回答这个问题，并且不让错误数据干扰结论。比如帧率 bug 会被误认为「时机太难」，这就是错误数据。

质量目标（按优先级）：

1. **判定正确：** 同样的输入得到同样的结果，包括打中/挥空、早/晚、界内/出界，不受帧率、设备和模式影响。
2. **手感：** 新手 60 秒内能打中第一拍，能理解「早 = 斜线、晚 = 直线」，并且想再来一局。
3. **公平：** 任何一方都没有漏洞、无脑最优打法或清零比赛的办法。AI 能被打败，但不是送分。
4. **稳定：** 没有 JS 报错，没有卡键，长时间玩不掉帧、内存不持续上涨。
5. **分享/上线时的安全：** 没有网络请求，不存数据，没有可注入的地方。

## 2. 范围

**测试范围内**
- 击球判定窗口、击球质量、物理与界内外判定、脚步与够球
- 与帧率无关（物理固定 240Hz 子步，`dt` 有上限）
- 输入：单人键盘、同一键盘双人（对战/双打）、触屏
- 四种模式的规则与计分，以及双打的分区站位
- AI 行为与难度平衡
- 并发与同步（同一步内的多个事件，暂停/重开/切模式时的竞态，多点触控）
- 静态文件的安全、异常与边界处理、玩法漏洞
- 桌面浏览器和手机的兼容性
- 可玩性（主观试玩）

**暂不测**
- 联网对战/网络同步、账号、排行榜、存档。等设计出来后再补一节策略（见 §12）。
- 音效。目前没有音效，只作为手感风险记录。
- 无障碍（HUD 缩放可读以外的部分）。正式发布前再看。
- 普通功能检查，比如「页面能打开」「按钮能点」。

## 3. 基于风险的测试重点

投入多少测试由风险决定。评级 = 发生可能性 × 对原型目标的影响。

| # | 风险 | 为什么重要 | 评级 | 对应测试 |
|---|---|---|---|---|
| R1 | 判定受帧率或设备影响 | 手感数据失去意义 | 高 | FPS-01..05、EXP-07、CMP-03 |
| R2 | 判定窗口和画面上的击球点对不上 | 玩家觉得「被吞了」，调参方向跑偏 | 高 | TIM-01..06、FUN-03 |
| R3 | 失焦、触屏滑动、暂停后卡键（蓄力或移动） | 这一回合打不了，还容易被当成时机问题 | 高 | INP-03/04、CON-08..12 |
| R4 | 双人同键盘按键冲突 | 某些键盘上双人模式没法玩 | 高 | INP-01/02、CON-01/02、EDG-09..11 |
| R5 | 判分错误或重复判分 | 玩家不再信任这个游戏 | 高 | RUL-01/02、PHY-06、CON-03、EDG-05/06 |
| R6 | 物理取舍手感不对（力量和出界、上旋和平击） | 核心深度没了 | 中 | PHY-01/02、调参试玩 |
| R7 | 漏洞或无脑最优打法（清零键、连按、打 AI 的安全点） | 对抗模式不公平 | 中 | EXP-01..09、AI 一节 |
| R8 | 出界只看球心，不看球的边缘 | 压线球被判出界，不符合网球规则 | 中 | PHY-03 |
| R9 | 真手机上的触屏（延迟、多点触控、来电等打断） | 手机手感还不知道，目前只做过无头测试 | 中 | INP-06/07、CON-08..11、CMP-02/03 |
| R10 | 上线后被注入或篡改 | 现在很低（静态、离线），加排行榜后变高 | 目前低 | SEC-01..08 |

之前探索时发现、本策略要跟踪到关闭的遗留问题：
- **EXP-01：** 双人/双打比赛中按 R 会清零比分。
- **CON-09 / CON-10：** 触屏滑动或鼠标在按钮外松开后，蓄力卡住。
- **PHY-03：** 压线判定。
- **RUL-06：** 还没有网球计分制（需要设计决定）。

## 4. 分层测试方法

| 层级 | 测什么 | 怎么测 | 负责人 | 时机 |
|---|---|---|---|---|
| L1 确定性检查 | 物理函数、`launchToward` 反解、时机窗口计算、计分状态变化 | 在无头 Chrome 里通过 `__tennis` 调试接口给固定输入、断言输出。快、可重复 | QA 自动化 | 每次改动 |
| L2 脚本化对局 | 机器人在每种模式打 N 秒。断言无 JS 报错、界内率合理、比分和事件对得上、没有 NaN | 无头 Playwright，用内置自动演示机器人，加上时间精确的模拟按键 | QA 自动化 | 每次改动 |
| L3 定向手工 | 需要人判断或真实硬件的边界和竞态场景（失焦、输入法、粘滞键、多显示器、多点触控） | 按用例手工执行，打开慢动作和 DevTools | QA | 每个改了输入、规则或参数的版本 |
| L4 探索式 | 带主题的测试：「想办法搞坏计分」「不靠时机打赢 AI」「只用手机玩」 | 每次 30–60 分钟，限时并记笔记 | QA + 开发 | 每个里程碑 |
| L5 试玩 | 手感和乐趣（FUN-01..05），找没见过这个游戏的人 | 5 人 × 10 分钟，计时、1–5 分打分、旁观记录 | 策划 + QA | 每次调参后 |
| L6 非功能 | 30 分钟长跑、CPU 降速、120/144Hz、浏览器和设备矩阵、安全评审 | DevTools 性能/内存面板，真机或云真机，代码评审 | QA | 每次扩大分享范围前 |

**原则：** 先修好 L1/L2 的失败，再做 L5。在有判定 bug 的版本上试玩，得到的调参反馈是错的。

| 3 物理（PHY） | L1 | 能（统计方式：每种设置打 N 拍，断言比率在区间内） |
| 4 脚步（MOV） | L1 + L2 | 能 |
| 5 输入（INP） | L3 | INP-02/04/05 能。INP-01/06/07 要真机 |

## 6. 手感和物理用统计方式判定

对局结果有随机性，所以这些用例不用「打一拍定成败」：
- **每种设置至少打 20–30 拍**，断言落在某个区间，而不是某个精确值。例如：平击满力，出界率 ≥ 70%。
- 调试接口支持时**固定随机种子**；不支持就在结果里记下种子或运行次数。
- 某个比率比上次基线**变化超过 15 个百分点**，即使还在区间内，也当作回归去查。
- 维护一张小的**基线表**（每种模式的界内率、完美率、AI 胜率），只有在有意调参后才更新。

## 7. 环境与设备

| 层级 | 环境 | 用途 |
|---|---|---|
| 开发循环 | 无头 Chromium（Playwright），60Hz，不降速 | 每次改动跑 L1/L2 |
| 压力 | Chromium CPU 降速 4x/6x、标签页切到后台、人为制造长帧 | 验证与帧率无关（R1） |
| 桌面矩阵 | 最新版 Chrome、Safari、Firefox、Edge。一台 120/144Hz 屏，一台 2 倍 DPI 屏，一台触屏笔记本 | CMP-01、FPS-02、EDG-08、EDG-14 |
| 键盘 | 一把便宜的薄膜键盘（测按键冲突）、一个 AZERTY 布局、中文输入法（拼音） | INP-01、EDG-09/10 |
| 手机 | 一台较新的 iPhone（Safari），一台中端、一台低端 Android（Chrome），横屏和竖屏 | INP-06/07、CON-08..11、CMP-02/03 |

目前最大的缺口是真机测试：到现在为止全是无头浏览器测的。在对手机手感下结论之前，先在真机上跑一轮。

## 8. 测试工具和数据

- **调参面板（13 个参数）：** 最主要的测试数据来源。每个 bug 和每次试玩结果都要记下当时的参数值。默认值：窗口 110ms、完美 30ms、满蓄力 0.7s、够球 0.95m。
- **慢动作（0.5 倍）：** 用来测边界用例（TIM、PHY-03/04）。结果还要在正常速度下再确认一次。
- **自动演示机器人：** 用来跑负载和长跑测试（L2、FPS-05）。
- **`__tennis` 调试接口：** 给 L1/EDG/CON 用例注入状态。测试版本要保留，**有计分排名或联网之前必须去掉或锁住**（SEC-04）。
- **DevTools：** 性能面板（CPU 降速、帧耗时）、内存面板（长跑时拍堆快照）、网络面板（SEC-01）、应用面板（SEC-02）。
- **手机 240fps 慢动作录像：** 测输入延迟（INP-07），以及画面击球点和判定点是否一致（TIM-06）。

## 9. 准入与准出标准

**准入（版本可以开始一轮测试）**
- 无头 Chromium 打开时控制台零报错。
- 四种模式的 L2 机器人冒烟各跑 120 秒，全部通过。
- 改动说明里列出改了哪些参数。

**准出：可以内部试玩**
- 所有 P0 用例通过，没有未关闭的 P0 缺陷。
- L1/L2 全绿，物理和界内率都在基线区间内。
- R1 和 R3 已覆盖：FPS-01、INP-03 和 CON 里的卡键用例都通过。

**准出：可以大范围分享或上线**
- 满足以上全部，并且所有 P1 用例通过，或写明理由豁免。
- 已完成一轮真机手机测试（§7）。
- SEC-03..07 和 EXP-01/02 已关闭，调试接口已锁住。
- 30 分钟长跑不掉帧、内存不上涨。
- 达到试玩目标：FUN-01 < 60 秒，FUN-04 平均 ≥ 3.5。

## 10. 缺陷管理

| 严重级别 | 定义 | 例子 | 处理目标 |
|---|---|---|---|
| S1 / P0 | 没法玩、判错分、卡键、比分被清零 | 双人对战中按 R 清零比分；触屏滑动后蓄力卡住 | 下次试玩前修好 |
| S2 / P1 | 明显影响手感或公平 | 压线球判出界；打 AI 有安全点 | 大范围分享前修好或豁免 |
| S3 / P2 | 打磨类、少见的边界情况 | 比分 99999 时记分板排版乱 | 放进待办 |

每个 bug 报告要写清：
- 模式、浏览器/设备、屏幕刷新率、当时的参数值
- 慢动作是开还是关
- 复现率（例如 7/10）
- 一段短录屏，因为时机类 bug 很难用文字说清

试玩中的「感觉不对」单独记成**手感问题**，和缺陷分开。手感问题在调参会上讨论，不算 bug 数。

## 11. 回归策略

| 改动类型 | 至少重跑 |
|---|---|
| 改了任何参数默认值 | TIM-01/02、PHY-01/02、FPS-01、AI 胜率抽样，然后做一次简短的 L5 试玩 |
| 物理或击球质量代码 | 全部 L1 + PHY + EXP-07 |
| 输入代码（键盘/触屏） | INP、CON-05..11、EDG-09..11、EXP-01..03 |
| 规则/计分代码 | RUL、DBL、CON-03/04/06、EDG-05/06 |
| 只改了画面 | L2 冒烟、FPS-05 长跑、CMP-01、EDG-07/08 |
| 新增模式 | 所有模式的 L2 冒烟，加上新模式的全部用例 |

把 L1/L2 写成一个无头脚本，这样一次回归只要几分钟，每次改完都能跑。

## 12. 阶段计划

1. **现在：手感原型。** 给 TIM/PHY/FPS/RUL 做 L1/L2 自动化，关闭已知 P0，跑第一次 5 人试玩。
2. **Alpha（可以分享文件）。** 真机手机测试、桌面浏览器矩阵、长跑、关闭 P1，并决定网球计分制（RUL-06）和压线判定（PHY-03）。
3. **上线网页。** 安全用例 SEC-06/07（CSP、frame-ancestors），锁住调试接口，检查托管的响应头。
4. **以后：联网对战或排行榜。** 需要新增一节策略，覆盖：
   - 服务器权威计分和反作弊（不再信任客户端）
   - 带种子的随机数，用于帧同步/回滚
   - 延迟和丢包模拟
   - 客户端之间的不同步检测
   - 断线重连和超时规则
   - 输入校验和频率限制
   - 存储玩家数据时的隐私

## 13. 角色分工

| 角色 | 职责 |
|---|---|
| 策划/负责人 | 定手感目标，决定规则（计分、压线、双人模式谁能暂停），批准调参基线 |
| 开发 | 修缺陷，保持调试接口可用、物理结果可复现；如果要做联网，加上带种子的随机数 |
| QA | 负责本策略、用例清单、自动化和真机测试，做探索式测试，汇报质量状态 |
| 试玩者 | 每轮 5 个以上没玩过的人，每轮换人，避免越玩越熟导致反馈偏差 |

## 14. 指标与汇报

每一轮测试汇报：
- P0/P1 通过率
- 按严重级别统计的未关闭缺陷
- 新增的手感问题
- 相对基线的变化：界内率、完美率、AI 胜率、低端机帧率
- 试玩得分：第一次打中的时间、「再来一局？」平均分

**状态规则：** 没有未关闭的 P0、基线都在区间内、并达到试玩目标，这一轮才算绿色。有没测的部分（比如没跑真机），要报**部分完成**，不能报绿色。
